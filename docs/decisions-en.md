# Flux Accepted Tradeoffs

> Existing compromises that are explicitly accepted — do not fix as defects. A new entry must state "why accepted" and "when to re-evaluate", and is appended at the end — existing entries are never reordered.
>
> Format: one problem per entry, and **the heading IS the problem** (the `T-xx` numbers are repo-wide reference anchors — code comments, `Cargo.toml`, CHANGELOG, and AGENTS.md all cite them — deliberately kept). Inside an entry, approach lines `- <date>: <approach>; advantage: …` are recorded in chronological order — the first approach's advantage states why it was chosen, a later one states what improved over the previous approach; **the latest line is the current approach**. Rejected/rolled-back approaches stay as their own lines (undated ones are marked as such — no dates are invented). Mechanism details link to the relevant architecture.md section (record, don't argue) instead of being re-argued here. The first-recorded date is the earliest surviving record of the entry in the current git history (history was squashed at v0.1.0 / v0.1.4 — the true first record may predate it).

## Accepted tradeoffs

### T-02 How to treat the arbitrary-execution risk of runner-class bash commands (first recorded 2026-09-12)

- 2026-09-12: Keep the first-word classification allow semantics — `eval`/`sudo`/interpreter-direct runners can execute arbitrary commands without smuggling, accepted as an inherent risk of that semantics, not a bypass (the notice always shows the full command); advantage: over the two rejected alternatives — a runner blocklist false-positives on legitimate authorized use, disabling first-word allow sacrifices convenience — keeping first-word allow avoids both costs. The approval layer is gone; this entry stays in case approvals ever return.

### T-03 Is the state tool's unknown-key read/write behavior a defect (first recorded 2026-09-12)

- 2026-09-12: Keep the generic KV semantics by design — writes accept any key, reads of unknown keys return the empty string; advantage: the behavior IS the feature — the agent's generic cross-round KV channel; the schema `enum` as guidance-only (not a whitelist) and read/write symmetry are constitutive of that purpose, and whitelisting would only remove the channel. Do not fix as a defect. Mechanism context: architecture.md, "Sandbox Semantics: workdir / current_dir" (boundary semantics live solely in the two authoritative keys `workdir`/`current_dir`).

### T-05 Explorer's directory git status: the git CLI or git2/gix (first recorded 2026-09-12)

- 2026-09-12: Keep shelling out to the `git` CLI — two calls per listed directory (`rev-parse --show-toplevel` + `status --porcelain -z`), already bounded by a `-- .` pathspec on the listed subtree, `-unormal` folding of untracked directories, and execution on the blocking thread pool; advantage: over `git2` (C toolchain dependency + unsafe + a worktree/config compatibility surface) and `gix` (pure Rust, but the high-level status API is still in flux and the dependency tree is heavy) — CLI compatibility and zero new heavy dependencies win, sufficient for the "re-list loaded directories every 15s" UI load. Mechanism context: architecture.md, "Web UI static serving → File explorer". Re-evaluate when: status calls become a measured hotspot (large-repo cold scan > several hundred ms), or the gix status API reaches stability.

### T-07 Streaming markdown rendering: swap the renderer or adopt a streaming library? (first recorded 2026-09-12)

- 2026-09-12: Keep marked + splitAndFold/ParagraphSplitter + renderStableSlice + FenceCache (researched and decided; do not re-propose a swap); advantage: over every candidate — ① marked has no incremental continuation API: the trailing `text` token absorbs unclosed inline constructs, so caching at token boundaries loses inline context; ② micromark's true streaming entry is Node-only, and the browser fallback degrades to a full re-parse (the O(n²) remains); ③ the ecosystem's "streaming markdown renderers" (streamdown, Vercel AI SDK, etc.) are actually remend self-healing of incomplete blocks + full re-parse + DOM diff, all carrying a React peer dep — the current pipeline's per-block caching / stable-prefix scheme is finer-grained than all of them, and the residual O(n²) lives only in pathological wall-of-text paragraphs (measured: 64KB ≈ 12ms, clamped to the current paragraph). Mechanism context: architecture.md, "Frontend: Streaming render". Re-evaluate when: a framework-free incremental renderer with a stable prefix-cache contract appears, or real-world inputs measurably exceed the frame budget.

### T-08 Long sessions hitting the context window: automatic pruning/compaction or manual splitting (first recorded 2026-09-14)

- 2026-09-14: Neither is built — the transcript stays a single accumulating context, no automatic budget pruning, no compaction/summarization; hitting the window surfaces as a provider 400 → round failure (error event), and recovery is the existing affordances — fork (restart from any user message), rebase, or a new chat — the user splits the context at a moment they choose; advantage: within typical single-user/small-team sessions overflow is rare, while automatic pruning/summarization would introduce the project's first archive boundary, dragging fork/rebase semantics, buf lifetime, and the proto along — complexity out of proportion to the current benefit.
  - Design essentials for a revival (absorbed from the shelf draft, not current behavior): 1) pruning granularity = whole rounds — a round is the pruning semantic unit, never split (see T-11: the store's atomic commit unit is the batch — each tool batch lands with its assistant segment, a round being several batches); 2) pruning only shapes the assembly view sent to the provider, the store is never rewritten, and large outputs of pruned rounds stay readable via buf_read (buf is anchored by call id and does not expire with the transcript) — the key enabler; 3) budget = context_window × safety factor (~0.7), estimator starts as chars/4 behind a trait; 4) compaction lands on the engine-rebuild primitive (machine gate + re-begin), the same path as a provider hot-swap; 5) compaction introduces the first archive boundary — fork points / rebase bases must live inside the surviving history, the UI needs a visible compression notice, and the store needs an archive table.
  - Re-evaluate when: overflow becomes a frequent pain point in real use (long sessions interrupted constantly, users tired of manually splitting), or a requirement appears that genuinely needs loading an oversized repository whole.

### T-09 Should Usage gain a cache-write wire field (first recorded 2026-09-14)

- 2026-09-14: No field — keep the derivation `W = max(0, in − cached)` (under OpenAI-compatible semantics cached ⊆ prompt, so the derivation is exact); advantage: a dedicated field only serves upstreams that report cache-write separately; every currently supported endpoint reports none, so the field would be constant-zero noise. Re-evaluate when: an upstream that reports cache-write separately is integrated (Anthropic-style usage, vLLM extensions), or cost estimation needs a cache-write price tier.

### T-10 Should the observability surface (/healthz, /metrics, round spans) be built (first recorded 2026-09-14)

- 2026-09-14: Not for now — no metrics endpoint, no health check, no round-level structured observability; stderr tracing only (plus the structured log fields on the self-healing/rebuild paths); advantage: for a single-process, single-user/small-team deployment bound to 127.0.0.1, logs answer every current diagnosis question, and a metrics surface (endpoint, histogram buckets, cross-crate static counters) would freeze a shape for an operations plane that does not exist yet.
  - Design essentials for a revival (absorbed from the shelf draft, not current behavior): 1) `/healthz` is pure liveness; `/metrics` is hand-rolled Prometheus text (fixed-bucket histogram + AtomicU64 counters, zero new dependencies); 2) counters are statics in flux-core (provider/chat/loop can all bump them), gauges (active_chats, mcp state) are read at scrape time; 3) instruments: round total/duration/failures, the three token totals, tool_calls, buf_writes, provider_retries; 4) round correlation = chat_id + round-sequence log fields, no OTel.
  - Re-evaluate when: deployed somewhere logs cannot attribute (multi-instance aggregation, long-running service SLAs), or "why was this round slow / which provider misbehaves" becomes a frequent diagnosis question.

### T-11 Server shutdown: graceful stop or crash-only (first recorded 2026-09-14)

- Date unknown (pre-squash): graceful shutdown — `with_graceful_shutdown` + drain waiting for connections to finish; advantage: no record (initial behavior; the motivation did not survive the history squash — this line exists to record the evolution).
- 2026-09-14: crash-only — install no signal handlers (SIGTERM/SIGINT keep their default dispositions; the process dies immediately, even with browser streams attached); durability rests unconditionally on the storage layer's contract; advantage: over the graceful shutdown above — ① it covers the smallest subset of death modes (SIGKILL, OOM, panic, power loss, container kill all bypass it), and data correctness must not depend on the death mode; ② waiting for connections was the very root cause of the old "must close the frontend to exit" behavior — a Subscribe body never completes on its own (the keepalive pump runs forever), `serve.await` was wedged behind in-flight streams permanently, and the drain never ran even once: zero value in its only needed scenario. The graceful-shutdown implementation is deleted.
  - Approach essentials: durability rests on the storage layer's contract — transcript commits are **batch-atomic** (the machine commits the assistant segment + the batch results at every batch boundary, before the stream resumes; the round's final segment commits at round end), and WAL + transactional writes guarantee every death mode lands at the same recoverable point — committed batches are never lost, the persisted tail never carries a dangling tool_call (OpenAI-compatible APIs 400 on those), and the crash window shrinks to the current live segment (seconds); tool-child cleanup does not ride the graceful path: in-process (`kill_on_drop` + process-group guard + cooperative cancellation) covers living children, and the kernel-side `PR_SET_PDEATHSIG` (flux-tools `arm_parent_death_signal`) covers every way the process itself can die. Mechanism context: architecture.md, "Conversation Loop" and "Persistence".
  - Residual cost (accepted): at shutdown the client sees a connection reset (RST), not a clean EOF — the client already reconciles via reconnect + the R2 snapshot, purely cosmetic; an unanswered tail message is re-sent by the user (the model sees the history, and the idempotency window dies with process memory anyway); a power loss can lose the last few commits (`synchronous=NORMAL` — zero loss on process crash, no per-commit fsync).
  - Re-evaluate when: a deployment appears that cannot accept the RST cosmetics, or needs "force-reap in-flight rounds before shutdown" (e.g. a multi-instance orchestration drain hook), and the storage layer's contract proves insufficient for recovery.

### T-12 Which layer strips ANSI from tool output (first recorded 2026-09-16)

- 2026-09-16: The strip lives ONLY in flux-tools `BashTool::execute` (before the result enters `bounded_output`) — not lifted into flux-chat's unified funnel, no frontend fallback; the capture layer is already a pipe (isatty=false) so isatty-aware programs turn color off themselves, and only isatty-ignoring programs (a tracing subscriber with the ansi feature is the typical case) need the strip; advantage: over "strip in the unified funnel" — minimal-scope fidelity: ① file tools (read_file/grep/glob) **never strip** — the model edits based on their content, and stripping would desync the model's view from the disk (character counts/offsets shift, edit round-trips fail); fidelity beats cosmetics; ② MCP results are not cleaned (protocol text, low risk); ③ no frontend fallback — history persisted before the change reopens with ANSI shown as-is, no data migration; ④ bare `\r` is dropped — progress-bar overwrite frames fold into a run of residue characters (the same tradeoff mainstream coding agents make stripping exec output). Re-evaluate when: color-emitting MCP tools become a frequent annoyance (generalizable to a per-tool hygiene declaration), or readability complaints about old history concentrate (a one-time migration scrub).

### T-13 skill activation dedup: dedicated table / directory watch, or transcript derivation (first recorded 2026-09-16)

- 2026-09-16: No dedicated table, no directory file-watching — the chat-owned `skill_read`'s activation index re-derives from the history at both assembly points (spawn / apply_rebuild; key = name + lexically-normalized rel), and the Tier-1 catalog is a begin-point snapshot; advantage: over a dedicated table — a table would add a second truth source plus fork keep-set copy SQL, while the transcript only grows (T-08), a committed skill_read result stays in the model's visible context forever, the transcript itself IS the activation record's source of truth, and fork / rebuild / restart inherit the dedup for free via re-derivation; over file watching (Claude Code watches) — flux's live-refresh surfaces are `skill_list`'s fresh scan on every call and `skill_read`'s unknown-name self-correction (global skills live outside the boundary, so skill_list is the only way to enumerate them).
  - Approach essentials: overflow = result chars > INLINE_BUDGET, overflowed content read back via buf_entries; a hit (same normalized-content hash) returns a short note instead of a second full injection (with the buf_read ref if it had overflowed), a miss returns the full text and is recorded — no new storage of any kind.
  - Accepted costs: the derivation's store reads happen only for overflowed skill paths (at most one per path; skill files are ≤256KB and paths are few); snapshot staleness is declared in the section text and pointed at `skill_list`; the lexically-normalized key (not canonical) costs at most one duplicate full read per in-skill symlink alias. Mechanism context: architecture.md, "Tool System → Agent Skills".
  - Re-evaluate when: catalog staleness demonstrably affects tasks at scale (revisit the SkillService install-triggers-a-gate-rebuild hook — the mechanism exists, only the wiring is missing), or compaction (when T-08 lands) requires switching the derivation source to the compacted view (the index semantics stay; only the input changes).

### T-14 Web UI asset resolution: disk-first chain, or embed into the binary + explicit override (first recorded 2026-09-17)

- Date unknown (pre-dating this entry): disk-first resolution chain — three disk candidates (CLI flag / next to the binary / flux home), with "binary refreshed, disk directory left behind" silent UI lag patched over by a version-stamp warning; advantage: no record (initial behavior — this line exists to record the evolution).
- 2026-09-17: rust-embed into the binary (feature `web-ui-embed`, default-on) — release builds embed, debug builds read the repo dist from disk at runtime (the path pinned to the compile-time `CARGO_MANIFEST_DIR` — the dev fallback); `~/.flux/web-ui` / `--web-assets-dir` drop to a **Gitea `custom/`-style per-path override** (same-named files shadow the embedded base, everything else falls through); advantage: over the disk-first chain above — that mismatch class is STRUCTURALLY IMPOSSIBLE on the embedded side (one build produces both), the override dir becomes the only mismatchable surface and keeps the stamp warning; the release pipeline drops the standalone `flux-web-ui.tar.gz` artifact and the `web-ui/` archive payload.
  - Accepted costs: ① building from source needs node/pnpm by default — without a toolchain, build.rs writes a placeholder page so the binary still compiles (`FLUX_WEB_UI_NO_BUILD=1` skips; `--no-default-features` for headless-only); ② rust-embed's macro expansion requires the folder to exist in ALL modes, which is what the placeholder guards; ③ new hashed filenames do not trip cargo's `include_bytes!` tracking — build.rs `rerun-if-changed` covers that; ④ binary +~2.5MB (woff2 fonts, incompressible); ⑤ a partial override can mix versions — inherent to explicit user customization, same as Gitea; ⑥ NO startup-time validation of the override dir / placeholder (the surviving part of the old T-06, merged here) — "agent available, UI pending" is not a fatal state; failures attribute at request time: index read failure → 500 + warn, missing assets → 404 (fail-fast was tried once and deleted). Mechanism context: architecture.md, "Web UI static serving".
  - Re-evaluate when: the placeholder page proves to genuinely mislead users (switch to fail-fast with fix instructions in the startup log), override-dir staleness becomes a real support burden (consider whole-directory validation or per-directory version gating), or multi-entry pages complicate the request-time failure shapes.

### T-15 Subset the terminal Nerd Font face or not (first recorded 2026-09-17)

- Date unknown (unrecorded): a subsetting experiment — cut to the prompt-icon ranges (~38 KB); advantage: dist/binary saves ~1 MB (under the then "~95% is file-icon families, pure redundancy" accounting).
- 2026-09-17: Rolled back — `JetBrainsMonoNerdFontMono-Regular.woff2` stays at its upstream full size (~1.0 MB) distributed with dist, **no subsetting**; advantage: over the subsetting above — the web terminal runs ARBITRARY REAL PROGRAMS, not just our prompt — Nerd glyphs printed by nvim/themes/`eza --icons` etc. all land in the Unicode Private Use Area (U+E000–F8FF plus a few scattered points), and **system fonts have no fallback for that range** — one missing glyph is one solid tofu block; in practice nvim was unusable after subsetting (user report). The "~95% redundancy" accounting only holds for static browsing, not for an interactive terminal — the in-face icon families (Material/Devicons/Codicons/Seti/Octicons/Weather) are exactly the code points third-party prompt/tool ecosystems reference, and "the browser terminal will never print those" was a wrong premise. Accepted cost: dist/binary +~1 MB (the largest single item in dist). Mechanism context: architecture.md, "Frontend: Layered Structure → Terminal tabs". Re-evaluate when: **no** static "by code-point list" subsetting qualifies — only when the browser platform offers dynamic font fallback (PUA ranges onto an installed NF font; CSS `unicode-range` depends on a known code-point list, which fails the same way), or the terminal introduces an explicit "output-glyph whitelist" contract (programs declare which private-area glyphs they use); even then it should become a lazily-loaded segmented face, not a cut-down single face.

### T-16 How should the streaming follow's detach signal be decided (first recorded 2026-09-17)

- Date unknown (pre-dating this entry): the detach signal = any scroll event reading as an up-scroll (no tolerance); advantage: no record (initial behavior — this line records the evolution's starting point).
- 2026-09-17: Tightened to **scrolled up AND ≥2px off the bottom** (goingUp && !nearBottomPx(pane, 2), the tolerance covering fractional-zoom rounding); a pinned goingUp event is treated as the renderer's clamp; wheel/pointer/touch user-input events are NOT adopted as the sole detach signal; advantage: over the initial behavior above — while pinned at the bottom, a boundary streaming render that nets NEGATIVE height (paragraph-commit reflow, code-fence fold-back removing committed nodes) makes the browser clamp scrollTop down and dispatch a scroll event that reads as up-scroll but is not the user leaving: one misjudgment detaches the stick state and every later scheduleFollow no-ops behind the gate until the user scrolls back into the 96px re-attach window (probabilistic when streaming an expanded reasoning block; a collapsed block never occupies the pane's scroll height and never triggers it) — clamp immunity + the tolerance give the follow structural survival. Not chosen: wheel/pointer/touch user-input events as the sole detach signal — a second listener surface enumerating input modalities, which jsdom cannot synthesize either. The alternative (re-syncing lastTop after programmatic writes) was not taken: the scroll event the write itself fires already syncs lastTop, and clamp immunity covers the same-frame write+shrink ordering. Accepted cost: the first ≤2px of a real scroll-up from the bottom may detach one event late — the next event always leaves the tolerance. Mechanism context: architecture.md, "Frontend: Streaming render → scroll follow". Re-evaluate when: the tolerance is shown to swallow a real user's first wheel tick (trackpad inertia first frames usually exceed 2px — low actual risk), or a new interaction must distinguish programmatic from user scrolling.
