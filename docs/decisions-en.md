# Flux Accepted Tradeoffs

> Existing compromises that are explicitly accepted — do not fix as defects.
> A new entry must state "why accepted" and "when to re-evaluate".

## Accepted tradeoffs

### T-02 Inherent risk of runner-class bash commands

Under the defense that classifies commands by their first word, `eval`/`sudo`/interpreter-direct runners can execute arbitrary commands without any smuggling — that is the inherent semantics of "allow by first word", not a bypass (the notice shows the full command). Rejected alternatives: a runner blocklist (false-positives on legitimate use), disabling first-word allow (sacrifices convenience). The approval layer is gone; this entry stays in case approvals ever return.

### T-03 The state tool's generic KV behavior

state writes any key / reads of unknown keys return an empty string — **by design** (a generic KV channel for the agent across rounds; the schema enum is guidance, not a whitelist; read/write are symmetric). Do not fix as a defect.

### T-05 Explorer git status via the git CLI, not git2/gix

`fsbrowse` shells out to `git` for directory status collection (two calls per listed directory: `rev-parse --show-toplevel` + `status --porcelain -z`), already bounded by a `-- .` pathspec on the listed subtree, `-unormal` folding of untracked directories, and execution on the blocking thread pool. `git2` (C toolchain dependency + unsafe + a worktree/config compatibility surface) and `gix` (pure Rust, but the high-level status API is still in flux and the dependency tree is heavy) are not introduced — for the UI load of re-listing loaded directories every 15s, CLI compatibility and zero new heavy dependencies win. Re-evaluate when: status calls become a measured hotspot (large-repo cold scan > several hundred ms), or the gix status API reaches stability.

### T-07 Streaming render pipeline keeps marked — no renderer swap, no streaming library

The streaming markdown pipeline stays on marked + splitAndFold/ParagraphSplitter + renderStableSlice + FenceCache (researched and decided; do not re-propose a swap): ① marked has no incremental continuation API — the trailing `text` token absorbs unclosed inline constructs, so caching at token boundaries loses inline context; ② micromark's true streaming entry is Node-only, and the browser fallback degrades to a full re-parse (the O(n²) remains); ③ the ecosystem's "streaming markdown renderers" (streamdown, Vercel AI SDK, etc.) are actually remend self-healing of incomplete blocks + full re-parse + DOM diff, all carrying a React peer dep. The current pipeline's per-block caching / stable-prefix scheme is finer-grained than those implementations; the residual O(n²) lives only in pathological wall-of-text paragraphs (measured: 64KB ≈ 12ms, clamped to the current paragraph). Re-evaluate when: a framework-free incremental renderer with a stable prefix-cache contract appears, or real-world inputs measurably exceed the frame budget.

### T-08 No context compaction; long sessions are managed manually by the user

The transcript stays a single accumulating context — no automatic budget pruning, no compaction/summarization (decided; both phases excluded). Hitting the model's context window in a long session surfaces as a provider 400 → round failure (error event); recovery is the existing affordances — fork (restart from any user message), rebase, or a new chat — the user splits the context at a moment they choose. Why accepted: within typical single-user sessions, overflow is rare; automatic pruning/summarization would introduce the project's first archive boundary, dragging fork/rebase semantics, buf lifetime, and the proto along — complexity out of proportion to the current benefit. Design essentials for a revival (absorbed from the shelf draft): 1) pruning granularity = whole rounds — a round is the machine's atomic commit unit, never split; 2) pruning only shapes the assembly view sent to the provider, the store is never rewritten, and large outputs of pruned rounds stay readable via buf_read (buf is anchored by call id and does not expire with the transcript) — the key enabler; 3) budget = context_window × safety factor (~0.7), estimator starts as chars/4 behind a trait; 4) compaction lands on the engine-rebuild primitive (machine gate + re-begin), the same path as a provider hot-swap; 5) compaction introduces the first archive boundary — fork points / rebase bases must live inside the surviving history, the UI needs a visible compression notice, and the store needs an archive table. Re-evaluate when: overflow becomes a frequent pain point in real use (long sessions interrupted constantly, users tired of manually splitting), or a requirement appears that genuinely needs loading an oversized repository whole.

### T-09 Usage cache-write stays derived — no wire field

`W = max(0, in − cached)` (under OpenAI-compatible semantics cached ⊆ prompt, so the derivation is exact), and the wire `Usage` gains no `cache_write_tokens` field. Why accepted: a dedicated field only serves upstreams that report cache-write separately; every currently supported endpoint reports none, so the field would be constant-zero noise. Re-evaluate when: an upstream that reports cache-write separately is integrated (Anthropic-style usage, vLLM extensions), or cost estimation needs a cache-write price tier.

### T-10 No observability surface (/healthz, /metrics, round spans) for now

No metrics endpoint, no health check, no round-level structured observability — stderr tracing only (plus the structured log fields on the self-healing/rebuild paths). Why accepted: for a single-process, single-user/small-team deployment bound to 127.0.0.1, logs answer every current diagnosis question; a metrics surface (endpoint, histogram buckets, cross-crate static counters) would freeze a shape for an operations plane that does not exist yet. Design essentials for a revival (absorbed from the shelf draft): 1) `/healthz` is pure liveness; `/metrics` is hand-rolled Prometheus text (fixed-bucket histogram + AtomicU64 counters, zero new dependencies); 2) counters are statics in flux-core (provider/chat/loop can all bump them), gauges (active_chats, mcp state) are read at scrape time; 3) instruments: round total/duration/failures, the three token totals, tool_calls, buf_writes, provider_retries; 4) round correlation = chat_id + round-sequence log fields, no OTel. Re-evaluate when: deployed somewhere logs cannot attribute (multi-instance aggregation, long-running service SLAs), or "why was this round slow / which provider misbehaved" becomes a frequent diagnosis question.

### T-11 Shutdown is crash-only: no graceful-stop mechanism; durability rests on the storage layer's contract

The server installs no signal handlers — SIGTERM/SIGINT keep their default dispositions and the process dies immediately, even with browser streams attached (the once-implemented graceful shutdown — `with_graceful_shutdown` + drain — is deleted). Why accepted: 1) graceful shutdown covers the smallest subset of death modes (SIGKILL, OOM, panic, power loss, container kill all bypass it) — data correctness must not depend on the death mode; 2) waiting for connections was the very root cause of the old "must close the frontend to exit" behavior — a Subscribe body never completes on its own (the keepalive pump runs forever), `serve.await` was wedged behind in-flight streams permanently, and the drain never ran even once: the mechanism had zero value in its only needed scenario; 3) durability rests unconditionally on the storage layer's contract: transcript commits are **batch-atomic** (the machine commits the assistant segment + the batch results at every batch boundary, before the stream resumes; the round's final segment commits at round end), and WAL + transactional writes guarantee every death mode lands at the same recoverable point — committed batches are never lost, and the persisted tail never carries a dangling tool_call (OpenAI-compatible APIs 400 on those), shrinking the crash window to the current live segment (seconds); 4) tool-child cleanup does not ride the graceful path: in-process (`kill_on_drop` + process-group guard + cooperative cancellation) covers living children, and the kernel-side `PR_SET_PDEATHSIG` (flux-tools `arm_parent_death_signal`) covers every way the process itself can die. Residual cost: at shutdown the client sees a connection reset (RST), not a clean EOF — the client already reconciles via reconnect + the R2 snapshot, purely cosmetic; an unanswered tail message is re-sent by the user (the model sees the history, and the idempotency window dies with process memory anyway); a power loss can lose the last few commits (`synchronous=NORMAL` — zero loss on process crash, no per-commit fsync). Re-evaluate when: a deployment appears that cannot accept the RST cosmetics, or needs "force-reap in-flight rounds before shutdown" (e.g. a multi-instance orchestration drain hook), and the storage layer's contract proves insufficient for recovery.

### T-12 bash output is ANSI-stripped only at the bash tool layer — no unified funnel, no frontend fallback

The capture layer is already a pipe (isatty=false), so isatty-aware programs turn color off themselves; for programs that ignore it (a tracing subscriber with the ansi feature is the typical case), the strip lives ONLY in flux-tools `BashTool::execute` (before the result enters `bounded_output`), not in flux-chat's unified funnel. Scope decisions: 1) file tools (read_file/grep/glob) **never strip** — the model edits based on their content, and stripping would desync the model's view from the disk (character counts/offsets shift, edit round-trips fail); fidelity beats cosmetics; 2) MCP results are not cleaned (protocol text, low risk); 3) no frontend fallback — history persisted before the change reopens with ANSI shown as-is, no data migration; 4) bare `\r` is dropped — progress-bar overwrite frames fold into a run of residue characters (the same tradeoff mainstream coding agents make stripping exec output). Re-evaluate when: color-emitting MCP tools become a frequent annoyance (generalizable to a per-tool hygiene declaration), or readability complaints about old history concentrate (a one-time migration scrub).

### T-13 Skill activation dedup derives from the transcript — no dedicated table, no directory file-watching

The chat-owned `skill_read`'s activation index re-derives from the history at both assembly points (spawn / apply_rebuild) — the transcript only grows (T-08), so a committed skill_read result stays in the model's visible context forever; the transcript itself IS the activation record's source of truth. A dedicated table would add a second truth source plus fork keep-set copy SQL. The Tier-1 catalog is a begin-point snapshot with no file watching (Claude Code watches; flux's live-refresh surfaces are `skill_list`'s fresh scan on every call and `skill_read`'s unknown-name self-correction — global skills live outside the boundary, so skill_list is the only way to enumerate them). Why accepted: the derivation's store reads happen only for overflowed skill paths (at most one per path; skill files are ≤256KB and paths are few); snapshot staleness is declared in the section text and pointed at `skill_list`. The lexically-normalized key (not canonical) costs at most one duplicate full read per in-skill symlink alias. Re-evaluate when: catalog staleness demonstrably affects tasks at scale (revisit the SkillService install-triggers-a-gate-rebuild hook — the mechanism exists, only the wiring is missing), or compaction (when T-08 lands) requires switching the derivation source to the compacted view (the index semantics stay; only the input changes).

### T-14 The browser UI embeds into the binary — disk is an explicit override only (no disk-first resolution)

`clients/web/dist` is embedded into flux-server via rust-embed (feature `web-ui-embed`, default-on): release builds embed, debug builds read the repo dist from disk at runtime (the path is pinned to the compile-time `CARGO_MANIFEST_DIR` — the dev fallback). `~/.flux/web-ui` / `--web-assets-dir` drop from "the disk-first tier of an asset-resolution chain" to a **Gitea `custom/`-style per-path override**: same-named files shadow the embedded base, everything else falls through. Why accepted: the old chain had three disk candidates (CLI / next to the binary / flux home), and "binary refreshed, disk directory left behind" silent UI lag was patched over with a version-stamp warning — with the embed that mismatch is STRUCTURALLY IMPOSSIBLE on the embedded side (one build produces both), the override dir becomes the only mismatchable surface and keeps the stamp warning; the release pipeline drops the standalone `flux-web-ui.tar.gz` artifact and the `web-ui/` archive payload. Accepted costs: ① building from source needs node/pnpm by default — without a toolchain, build.rs writes a placeholder page so the binary still compiles (`FLUX_WEB_UI_NO_BUILD=1` skips; `--no-default-features` for headless-only); ② rust-embed's macro expansion requires the folder to exist in ALL modes, which is what the placeholder guards; ③ new hashed filenames do not trip cargo's `include_bytes!` tracking — build.rs `rerun-if-changed` covers that; ④ binary +~2.5MB (woff2 fonts, incompressible); ⑤ a partial override can mix versions — inherent to explicit user customization, same as Gitea. ⑥ NO startup-time validation of the override dir / placeholder (the surviving part of the old T-06, merged here) — "agent available, UI pending" is not a fatal state; failures attribute at request time: index read failure → 500 + warn, missing assets → 404 (fail-fast was tried once and deleted). Re-evaluate when: the placeholder page proves to genuinely mislead users (switch to fail-fast with fix instructions in the startup log), override-dir staleness becomes a real support burden (consider whole-directory validation or per-directory version gating), or multi-entry pages complicate the request-time failure shapes.
